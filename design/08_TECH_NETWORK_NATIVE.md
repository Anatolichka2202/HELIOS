# HELIOS — платформенная архитектура, нативные клиенты и сервер
**Версия:** Draft 0.3 · **статус:** проектное решение, сервер пока **НЕ развёрнут**.

## Краткое решение

Три самостоятельных клиента + общие правила/данные и сценарные тесты. **Базовая одиночная игра обязана работать офлайн**. Сервер вводим по реальной необходимости: облачные сохранения, кооператив, рейтинги с честностью или опциональные ресурсоёмкие расчёты. Не переносить экономику на сервер только потому, что «облако мощнее».

## 1. Слои системы

```text
                           design/ (канон, сюжеты)
                                    |
                 shared/ (схемы, IDs, units, content)
                                    |
                     validation + golden scenarios
                         /          |           \
                        /           |            \
             lite/ JavaScript  mobile/ C#    pc/ UE5 C++
            F0 simulation        F1 model       F2 model
               2D DOM/UI        3D diorama      3D strategy
                                                     + first-person
                        \           |          /
                         optional account/saves
                                 |
                     optional API + job queue
                         /              \
                 async heavy solver     online session server
                       (F3)              (later co-op)
```

На раннем этапе F0/F1/F2 используют **общие контракты**, но могут иметь собственные расчётные реализации. Утверждение «общий движок C++ для всех платформ» сейчас **не соответствует коду**.

## 2. Клиенты / «нативность»

| Клиент | Реализация | Результат | Общее |
|---|---|---|---|
| Lite | HTML/CSS/JS; TypeScript после UX-стабилизации | Запуск в браузере, не нативный .exe/.apk | shared schema, сценарии и контент |
| Mobile | Unity 6, C#, IL2CPP где требуется платформой | Нативно упакованное Android/iOS приложение через игровой движок | контракты/IDs + C# реализация F1 |
| PC | Unreal Engine 5, C++, Blueprint/UMG | Нативный исполняемый Windows-клиент | контракты/IDs + C++ реализация F2 |

**Не писать** игровую стратегию на SwiftUI/Kotlin Views только ради нативности: они потребуют двойной реализации UI/3D. Разработка нативных расширений на Swift/Kotlin допускается для входа, уведомлений, платформенной авторизации и платежей, когда это действительно необходимо. Unity использует собственный рендер/runtime, но собирает реальные приложения, а не WebView.

**Важная альтернатива:** общий C++ engine на F2 + C ABI wrapper для Unity Android/iOS и Emscripten/WASM для Lite. Плюс — единый расчётный код; минусы — build matrix, сложности FFI и памяти, диагностика WASM, размер доставки, AOT/подписи, невозможность просто отдавать UE UObject в Unity. **Не делать сейчас**. Оценить через spike после стабилизации первого сценария.

## 3. Как устроена симуляция без сервера

- Пользователь отправляет команду.
- Домен проверяет инварианты/права/запасы и генерирует новое состояние и события.
- Отдельный фиксированный `simTick`; графический UI читает только snapshots.
- Сохранение содержит snapshot, версию и метаданные источника, а на PC может содержать журнал команд для отладки.
- В одиночной игре игрок может останавливать/ускорять время без сетевого консенсуса.
- Время FPS/рендера не должно изменять производственные ресурсы или вероятность аварии.

Большие научные и орбитальные задачи решаются упрощённой таблицей/интерполяцией; для PC или отдельных научных миссий можно запускать более точный solver в отдельном потоке/процессе и показывать ожидаемую погрешность.

## 4. Когда сервер реально имеет смысл

### Stage S0 — сейчас: полностью офлайн
Lite — статический HTTPS-хостинг, `localStorage`; Mobile — локальные сохранения; PC — локальные файлы. Никакого обязательного backend. Страница подписки на новости — отдельный обычный веб-сервис позже, не игровой сервер.

### Stage S1 — аккаунты/облако при потребности
Опциональная авторизация/синхронизация состояния внутри одного продукта, восстановление сохранения, согласованная версия контента. Не обещать прямой перенос SaveGame Lite ↔ PC из-за разной механики.

Пример API: `GET /v1/me/saves`, `POST /v1/saves`, `GET /v1/saves/{id}`, `DELETE /v1/saves/{id}`; API-key/public token в клиенте **не** должны давать административные права. Авторизация по токенам, ограничение размеров/запросов, управление удалением данных.

### Stage S2 — дорогие вычисления (опционально)
Игрок исследует сложный проект: орбитальная доставка крупного корпуса, ресурсный прогноз, проект экранирования Венеры. Клиент формирует **малую входную задачу** и отправляет асинхронный job:
```text
Client F1/F2 -> POST /v1/solver/jobs
  {modelVersion, inputHash, inputs, maxWork, seed}
  -> API validates quotas and schema
  -> queue -> CPU/GPU worker -> stored result
Client polls status or receives push -> compares with local approximation
```
Результаты versioned, кэшируются и выдаются с оценкой погрешности. На слабом телефоне **локальный approximation остаётся играбельным** при отсутствии сети. Никакой оплаты вычислений, дающей преимущество в общей соревновательной игре.

**Не отправлять каждую секунду всю симуляцию на сервер**: сетевые задержки, outages, стоимость и проблемы мобильной связи могут быть хуже локального F0/F1.

### Stage S3 — кооператив PC после успешного single-player
Один авторитетный процесс сессии, несколько игроков с ролями/правами. Отправка команд -> ordering/validation -> серверный tick -> состояние/события -> clients. Для скорости игры при голосовании/пауза в кооперативе нужны правила, которые не будут разрушать работу участников. Начинать с 2–4 человек, одной станции; не MMO на тысячи игроков. Рейтинг/PvP потребует защиты от читов, антиспама и иной бизнес-модели и **не обязателен**.

## 5. На чём писать сервер

**Если S1/S2 станет нужным:** удобный старт — Python/FastAPI для API и orchestration, PostgreSQL для пользовательских данных после появления реального объёма, очередь заданий при дорогих расчётах; отдельный C++ solver можно запускать как worker или библиотеку, если бенчмарк показывает необходимость. Для локального эксперимента SQLite/файловая очередь достаточно.

Выбор backend **не окончательный**. Пользовательский игровой клиент не должен зависеть от Python-сервера для одиночной кампании.

Конкретные компоненты и облачный провайдер — только после требований к нагрузке. Не привязываться заранее к Kubernetes, Redis и GPU. Всегда отделять стоимость хранения аккаунтов от стоимости вычислительных задач.

## 6. Надёжность и управление версиями

- Offline-first, no single point of failure.
- У команд ID и допустимое время/номер шага; повторные запросы API идемпотентны.
- Общие схемы `schemaVersion`, сериализация контрактных данных и ошибок.
- Сервер не доверяет стоимости, записанной клиентом, если игра с общими ресурсами/соревнованием.
- Локальное сохранение и резервные копии, миграции, проверка целостности.
- Логи без личных данных где возможно, минимальная телеметрия по согласию.
- Backend считает CPU-секунды/память/ошибки/стоимость одного solver-job до масштабирования.
- Отдельные CI: JS/Node, C++ CMake, Unity build test, UE build+packaging (когда доступно).
- Доступны тестовые golden cases: герметизация, нехватка питания, рейс, отказ платформы, финансовый контракт.

## 7. Performance и сложности моделирования

Реалистичный цельный atmospheric CFD + орбитальный N-body + социальная модель на каждом такте не нужна для стратегии. Большую часть игрового значения даёт **умный агрегатный моделлер**: mass/energy accounting + расписание перевозок + риски + событийная симуляция. Высокая точность должна иметь конкретное назначение, а не быть аргументом для продажи серверов.

Улучшения:
- Fixed step и упрощённые области;
- approximate precomputed transfer windows;
- адаптивная детализация по зонам;
- повторный расчёт только изменившихся узлов (dirty flags/dependency graph);
- offline background processing в PC с отменой;
- серверная асинхронная тяжёлая задача только при обоснованном UX и runtime.

## 8. Стартовые контрольные критерии

1. Без сервера Lite и Mobile завершают венерианскую сессию; PC — локальный vertical slice.
2. Состояние сериализуется с версией, на ошибку команда возвращает причину, без частичной мутации.
3. Нет дублирования ID/констант без проверки контракта.
4. Сложный F3 проект показывает «можно рассчитать локально приблизительно» и **не блокирует прогресс**.
5. Сетевая архитектура ни копейки не стоит в покое, потому что сервис не развернут до доказанного спроса.

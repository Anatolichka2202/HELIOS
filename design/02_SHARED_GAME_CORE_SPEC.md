# HELIOS — обязательное общее игровое ядро
**Версия:** Draft 0.3 · **область:** все три продукта · **статус:** спецификация для последующей реализации

## 1. Не «один движок рендера», а одна система понятий

Обязательный общий слой — не Unreal Engine и не Unity, а **игровой домен с версионированными правилами и тестируемыми контрактами**. Он содержит ресурсы, объекты, действия, технические ограничения и последствия. Клиенты могут рендерить их по-разному.

Минимальные сущности:

- `World` / `CelestialBody`: тело, позиция/орбитальные параметры там, где нужны, среда, ограничения по местоположению.
- `Region`: орбита Венеры, облачный слой, нижняя атмосфера, поверхность; далее — региональные узлы других тел.
- `Site`: станция, платформа, объект промышленности, наземная база или транспортный узел.
- `InfrastructureModule`: назначение, уровень, долговечность, входы/выходы, мощность, персонал, ремонт, аварийность.
- `Resource` / `Inventory`: материалы и расходники в хранилищах; запрет отрицательных запасов.
- `PowerNetwork`: производство, потребление, резервы, критичность модулей, отключение при дефиците.
- `Route` / `Shipment`: источник, получатель, тип груза, масса, вместимость, стоимость, время прибытия, риск.
- `ResearchProject`: требования, затраты времени и научных данных, достижимый результат.
- `Programme`: портфель инвестиционных проектов, бюджет, поддержка и обязательства.
- `Faction`: научные, государственные, международные, промышленные и общественные интересы.
- `Character`: биография, роль, доверие и отношение к событиям; возможно доступен только кампании.
- `Scenario` / `Objective`: начальные условия, победа/поражение, кампанийные ограничения или свободная сессия.
- `Event` / `Decision`: триггер, требования, варианты, измеримые последствия и текстовое представление.

Обязательный минимальный комплект для первого рабочего сценария: Region, Site, Module, Resources, Power, Shipment, Research, Programme, Event, Objective. Политические фракции и персонажи первоначально могут быть упрощёнными.

## 2. Элементарный системный цикл

```text
Команда игрока
  -> проверка прав/требований/ресурсов
  -> резервирование ресурсов и запуск проекта
  -> фиксированный шаг симуляции
  -> производство и потребление
  -> прибытие и отправка грузов
  -> износ/опасности/аварии
  -> исследования и события
  -> проверка целей
  -> снимок состояния + журнал последствий
  -> локальная визуализация
```

При отклонённой команде никаких изменений состояния. Действия не должны зависеть от FPS, а клиент не должен вносить прямые изменения в доменные запасы без команды.

## 3. Временные масштабы

В каноне события имеют дату/временную шкалу, но расчётные шаги разные:
- Lite: один **условный ход экспедиции**, в текущем коде показан как год. В следующей версии проверить замену на месяцы/кварталы: двухгодовая доставка как константа сейчас не соответствует реальным транспортным окнам.
- Mobile: дискретный период (неделя/месяц) с паузой, ускорением и офлайн-продолжением только после явного выбора игрока. Никакого механизма «возвращайся через 18 часов» как бизнес-основы.
- PC: фиксированный системный шаг, например условный день, с ускорением до месяцев/лет; агрегированные подсистемы на более грубом шаге.

**Инвариант:** результат не зависит от кадровой частоты. Точное равенство траекторий между продуктами не требуется из-за разных уровней детализации.

## 4. Согласованные единицы и уровень достоверности

Отдельно различаем:
- **SI-модель:** масса кг/т, энергия Дж/кВт·ч, мощность кВт/МВт, время сек/сутки, стоимость в бюджетных единицах, температура K, давление Па/бар. Используется в продвинутой симуляции.
- **Игровые упрощения:** бюджетные единицы, очки науки, интегральная надёжность 0–100. Используются в Lite/Mobile для доступного управления.

Правило: денежные единицы и очки науки не складываются и не выдаются за реальные физические вещества. В отображении допустимы «тонны» и «МВт» **только** когда их действительно считает модель. Технический паспорт объектов описывает допущения и расчётные величины.

Слой точности (fidelity tiers):
- `F0`: Lite — дискретные цепочки и табличные риски.
- `F1`: Mobile — агрегированные объекты, прогнозы/резервы/транспорт и упрощённые сети.
- `F2`: PC — детальные потоки, подсистемы надёжности, перевозки, параметры среды.
- `F3`: экспериментальный научный расчёт — отдельный solver/worker для сложных оптимизаций. Не обязателен для базовой игры.

## 5. Обязательные законы геймплея

1. Ничего нельзя построить из отрицательных ресурсов.
2. Любой производственный объект требует времени, входных материалов, энергии, персонала/автоматики и дальнейшего обслуживания.
3. Полезные материалы не появляются без источника и отходов; в Lite допускается явно помеченное «внешнее финансирование».
4. Нет бесплатной мгновенной логистики: маршрут имеет время и пропускную способность; поставка может задержаться или погибнуть.
5. Модуль при дефиците питания имеет определённый переход — понижение режима, остановка, повреждение, а не невидимое исчезновение.
6. Исследование открывает технологию/надёжность, но само по себе не создаёт станцию.
7. Отказы предсказуемы по seed/условиям, логируются и имеют варианты реагирования.
8. У игрока есть минимум две осмысленные альтернативы для ключевых сюжетных/инженерных решений.
9. Все состояния победы и поражения вычисляет домен, а не экран.
10. Затраты/доходы и причины событий объяснимы в интерфейсе («почему?» и «что изменится?»).

## 6. Команды и события

Формат будущего протокола (пример, не production):
```json
{
  "schemaVersion": 1,
  "scenarioId": "venus-foundation",
  "tick": 142,
  "actorId": "player-1",
  "commandId": "cmd-000142-a",
  "type": "schedule_shipment",
  "payload": {
    "fromSiteId": "earth-orbital-hub",
    "toSiteId": "venus-cloud-site-01",
    "resourceId": "spare-parts",
    "massKg": 200
  }
}
```

Ответ: `accepted` или типизированная ошибка, номер шага, `stateVersion`, события, затронутые сущности, новый hash/контроль состояния для отладки. Для офлайн-игры весь цикл исполняется внутри клиента. Для серверной — авторитетен backend. Нельзя обещать побитовую идентичность floating-point реализации разных движков без профилирования/специальной арифметики.

## 7. Структура сохранения

`SaveGame`: `saveSchemaVersion`, `gameBuild`, `scenarioId`, `worldVersion`, `seed`, `tick`, `playerDecisions`, `stateSnapshot`, `contentVersion`, `checksums` (для целостности, не как криптографическое доказательство честности). Поле version обязательно; миграции тестируются.

**Не требуем перенос сохранений между Lite, Mobile и PC в MVP** — игровые правила не идентичны. Вместо этого допускается перенос **метаданных достижений или открытого канона** в будущем.

## 8. Архитектурная стратегия

### Рекомендую сейчас
1. `shared/`: раздельные JSON схемы и контентные таблицы + JSON Schema + валидатор + golden scenarios.
2. `lite/engine.js`: оставить действующий JavaScript proof-of-concept, усилить тесты, убрать из него дублирующие ID через data generation/JSON.
3. `core/`: C++17/20 headless research. Не объявлять его production core до сравнения правил с Lite.
4. `mobile/` и `pc/`: сначала UI/визуальный вертикальный срез, затем адаптеры к общей спецификации, а не преждевременный C++ плагин.
5. После 1–2 проверенных сценариев решить, нужен ли общий **C++ simulation library** для UE + Unity (native plugin/iOS/Android ABI) и WebAssembly для Lite. Это технически возможно, но усложняет CI, FFI, сборки и диагностику; альтернатива — общий schema + golden tests, отдельные реализации для классов точности.

### Решение на текущую стадию
**Единое ядро — единая спецификация + воспроизводимые тесты и данные, пока НЕ единый бинарный модуль**. Не тратим первый коммерческий цикл на универсальный SDK, когда правила ещё меняются ежедневно.

## 9. Обязательные тесты

- Unit: сохранение ресурсов, запрет отрицательных значений, стоимость команд, состояние сети.
- Property: одинаковые входы/seed -> одинаковый итог в одном и том же backend/сборке.
- Fuzz: некорректный JSON, неожиданные даты, повреждённые сохранения.
- Scenario golden: запуск зонда, запуск аэростата, изоляция груза, отказ питания, восстановление, провал миссии, договор с партнёрами.
- Integration: UI не меняет состояние в обход API.
- Cross-product contract: ID, схема и инварианты совпадают, а fidelity tiers перечисляют допустимые отличия.

## 10. Критерий готовности общей модели v1

Все три клиента распознают одинаковые ID Венеры и видов оборудования, умеют отображать понятные ошибки и участвуют в одних базовых сценариях. В Lite и Mobile пользователи могут закончить маленькую сессию без сервера. PC не блокируется запуском тяжёлого вычислителя, если сценарий не требует F3.

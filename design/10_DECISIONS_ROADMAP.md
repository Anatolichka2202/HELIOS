# HELIOS — решения, очередность разработки и критерии продолжения
**Версия:** Draft 0.3 · 22.10.2026 · **цель:** не потерять проект при параллельной разработке трёх клиентов.

## 1. Реальная точка старта

GitHub `Anatolichka2202/HELIOS` содержит:
- браузерный код `lite/` со сценариями Венеры, экономическими правилами, тестами и SVG-артом;
- Unreal C++ scaffold `pc/`: венерианский актор и заготовки модуля, редакторная сборка не подтверждена;
- Unity C# scaffold `mobile/`: каталог и примитивная визуализация Венеры, мобильная сборка не подтверждена;
- C++ research core `core/`: **не** общий runtime игры;
- `shared/venus-scenario.json`: скромный общий data contract;
- старые эксперименты и документы в `archive/`, `design/originals/`;
- GitHub Issues и CI-конфигурацию. Отдельная GitHub Projects доска пока не подтверждена.

## 2. Принятые рабочие решения

| Область | Что делаем | Почему |
|---|---|---|
| География | Франшиза — вся Солнечная система, вертикальный срез — Венера | Не расширять scope до появления основного цикла |
| Жанр PC | Narrative industrial strategy с ограниченным first-person | Не сводить проект к режиму бога и не создавать FPS |
| Жанр Mobile | Touch-first colony & logistics strategy | Самостоятельная ценность на маленьком экране |
| Жанр Lite | Короткая пошаговая инженерно-сюжетная стратегия | Быстрая публикация и проверка решений |
| Сюжет | Советский архив (художественная альтернативная история) → Россия → международная программа | Основа канона всех клиентов |
| Офлайн | Single-player полностью офлайн на всех клиентах | Доступность, стоимость и долгосрочная поддержка |
| Runtime | PC Unreal/C++; Mobile Unity/C#; Lite JS с возможным TS | Соответствие текущим наработкам, не переписывать всё |
| Общий слой | Данные, единицы, события, команды, сценарные тесты | Единая предметная модель без ненужного FFI |
| Сервер | Только опционально по мере проверки потребности | Нет неоправданных затрат и зависимости от сети |
| Коммерческий подход | Free Lite -> спрос -> Mobile paid hypothesis -> PC premium | Снижать риск, не ждать всей AAA-игры |
| Качество | Тесты, smoke билд, фактические устройства, ясный статус | Не подменять реальную сборку исходниками |

## 3. Гипотезы, не решения навсегда
- Нужна ли мобильной игре 3D-диорама или будет достаточно качественного 2.5D.
- Нужен ли PC масштабный first-person или лишь 2–3 сильных сюжетных локации.
- Надо ли разделять C++ симуляцию в общий нативный SDK/Unity plugin/WASM, или достаточно общих данных и golden tests.
- Будут ли игроки покупать Mobile за разовый unlock, PC по premium цене, Lite дополнения.
- Достаточно ли на PC локальной модели F2; где реально полезен серверный solver F3.
- Когда и как реализовывать кооператив PC.
- Какую дату, возраст и имя получает главный герой.

**Правило решений:** под каждую гипотезу писать минимальный эксперимент и заранее определять, какое наблюдение изменит наш план.

## 4. Разработка по вертикальным результатам

### Milestone M0 — инженерный порядок
**Цель:** установить то, что реально запускается и для чего предназначено.
- Проход `docs/CODEBASE_MAP.md`; единый индекс docs.
- Запуск Lite тестов в CI, CMake Debug + Release, проверка сохранений.
- UE compilation smoke; Unity compilation/build smoke на выбранных устройствах.
- Раздельные каталоги source, archive, art, build artifacts.
- Обновить issue статусы и предусмотреть pull request review вместо неограниченных автоматических push в main.

**Готово только если:** все клиенты имеют воспроизводимую инструкцию запуска и честную отметку сборки; одна точка правды о границах кода.

### Milestone M1 — публичная Venus Lite
**Цель:** ссылка, которую реально открывают с iPhone, и законченное начало игры.
- Настроить GitHub Pages/другое static HTTPS; проверить публичный URL.
- Прогнать реальные touch flows (не только JS tests).
- Улучшить интерфейс подсказок, финал с разбором, понятные расходы/прибытие грузов.
- 1 кризис с двумя отличающимися решениями.
- Отличимые этапы визуального развития Венеры.
- 15–30 внешних плейтестов с согласия участников.

**Готово только если:** незнакомый игрок проходит пролог и может объяснить, почему его станция работает/погибла.

### Milestone M2 — общий экономический контракт
**Цель:** избежать трёх разных игр по названию одних кнопок.
- Ввести JSON Schema для regions, resources, facilities, costs, events, scenarios.
- Утвердить единицы, не смешивать кредит/кВт/кВт·ч.
- Массобаланс/производственные цепочки и пороги обслуживания.
- 10+ golden-command scenarios и cross-product validator.
- Решить нужна ли унификация симуляционного ядра **по доказанной потребности**, не до.

**Готово только если:** понятная спецификация объясняет один и тот же кейс (например отказ аэростата) во всех трёх продуктах, а различия детализации задокументированы.

### Milestone M3 — Mobile Venus playable
**Цель:** первый реально работающий touch client.
- Unity editor compile, камера, одна детализированная атмосферная станция.
- Список проектов, понятный статус, 1 цикл поставки/обслуживания/решения.
- Сохранение и полное офлайн прохождение.
- Android device smoke; позже iOS device smoke.
- UX исследование: понятна ли мобильная стратегия без PC-камеры/первого лица.

**Готово только если:** реальный Android/iOS пользователь способен сыграть локальную сессию, а не просто повращать сферу.

### Milestone M4 — PC Venus vertical slice
**Цель:** доказать отличие от Lite/Mobile и смысл дорогого Unreal-производства.
- UE Windows build, камера и видимый прогресс строительства.
- Энергия, логистика, аэростат, отказ, ремонт, сохранение.
- Один осмысленный эпизод от первого лица с тем же объектом/состоянием.
- Один качественный арт/звуковой сценический пакет, профилирование.
- Сравнительный плейтест «только стратегия vs стратегия + first-person».

**Готово только если:** PC-срез интересно играть, а не только смотреть на красиво освещённую Венеру.

### Milestone M5 — доказательство коммерческой модели
**Цель:** не покупатели «на словах», а подтверждённое предложение.
- Анализ плейтестов, ожиданий и вариантов покупки.
- Проверка мобильного premium/unlock и PC wishlist/дэмо.
- Финансовая модель с нулевым и оптимистичным сценариями.
- Решение о масштабировании только после оценки себестоимости и реального интереса.

## 5. Что делать прямо в следующий рабочий цикл

1. Открыть ссылку на браузерную игру по HTTPS на iPhone и проверить один полный сценарий, иначе все интерфейсные улучшения бессмысленны.
2. Привести GitHub Actions к зелёным тестам, а не считать сам YAML успешным CI.
3. Перепроверить баланс текущего Lite и отрезки времени, убрать «условные два года доставки» из интерфейса, заменить моделью хода.
4. Создать в `shared/` настоящую схему ресурсов и команд, с тестами.
5. Установить UE5 на тестовой машине, собрать `pc/`, исправить компиляцию, сохранить build report.
6. Установить Unity 6 и собрать `mobile/` на Android.
7. Подготовить одно тестовое целевое впечатление: ракета/станция в облаках, которую можно построить и спасти от аварии.
8. После работающей демки показывать её людям, а не тратить всё время на новые проектные документы.

## 6. Приоритеты при ограниченной трудоёмкости

**Одна интеграционная ветка модели; три фокусных клиента.** Для одного разработчика или маленькой команды полезно условно выделить основной производственный поток на Lite+shared, меньшую часть — компиляционные/визуальные spikes PC и Mobile, ещё меньшую — арт и коммерческую проверку. Распределение времени определяется фактическим результатом, не обещанием параллельных больших релизов.

Не запускать одновременно разработку полного сюжета PC, сетевого режима, iOS оплаты, тяжёлого solver и Марса до рабочего первого цикла Венеры.

## 7. Definition of done для задачи GitHub
- есть issue с намерением и критерием;
- код/данные/арт в Git;
- PR или коммит однозначен;
- проверки на CI/устройстве с реальными результатами, иначе пометка «не проверено»;
- актуальны README, спецификация, тесты и реестр ассетов;
- понятно, какой новый пользовательский результат получен.

## 8. Чего нельзя объявлять завершённым
GitHub Project board без подтверждённой ссылки, public Lite demo без настоящего URL, UE/Unity «собрана» без компиляции, first-person «реализован» только потому что есть камера, «графика готова» из-за одного концепт-арта, monetization «работает» без платежей, `core/` «shared» без интеграции.

## 9. Контроль видимости и IP
Репозиторий сейчас публичный. Решение о лицензировании, правах на сюжет/ассеты, разделе открытых модулей и закрытых производственных ресурсов — отдельное управленческое решение. Не коммитить чужой код и коммерчески неочищенные изображения. Для крупных бинарников при необходимости Git LFS/asset storage, не бездумное хранение гигабайт в истории Git.
